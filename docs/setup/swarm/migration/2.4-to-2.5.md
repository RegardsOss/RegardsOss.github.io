Steps to migrate REGARDS from version 2.4 to 2.5

## Playbook modifications

- Download last playbook version (especially all roles) and move your inventory inside the new playbook
- Edit your inventory file `group_vars/all/main.yml` :

```yaml
# Replace 
version: 2.4.X
# Into 
version: 2.5.Y
```

- Shutdown REGARDS using the playbook

```bash
ansible-playbook --ask-pass --ask-become-pass -i [...] regards-shutdown.yml [...]
```

Or if your inventory use a vault system to encrypt credentials

```bash
ansible-playbook --ask-pass --ask-become-pass --ask-vault-pass -i [...] regards-shutdown.yml [...]
```

- Remove old plugins from NFS as their name may have changed

```bash
ansible-playbook --ask-pass --ask-become-pass -i [...] regards-delete-plugins.yml [...]
```

Or if your inventory use a vault system to encrypt credentials

```bash
ansible-playbook --ask-pass --ask-become-pass --ask-vault-pass -i [...] regards-delete-plugins.yml [...]
```

- Update REGARDS using the playbook

```bash
ansible-playbook --ask-pass --ask-become-pass -i [...] regards.yml [...]
```

Or if your inventory use a vault system to encrypt credentials

```bash
ansible-playbook --ask-pass --ask-become-pass --ask-vault-pass -i [...] regards.yml [...]
```

During startup and before RabbitMQ migration, some REGARDS services will be unavailable.

- Wait for the stack REGARDS to be up and running

```bash
cd /path/to/regards/cli
./status.sh
# Check every containers of RabbitMQ are up and running
```

## RabbitMQ Configuration

If you have any queue or shovel bound to the exchange `regards.storage.file.notification`, please follow the
instructions below.

For each queue or shovel bound to the exchange `regards.storage.file.notification`:

* If the binding key is `#`, you may leave the queue/shovel as-is. However, consider the recommendation below for
  improved security and efficiency.
* If the binding key is `regards.file.availability.status`, you must re-create the queue/shovel. For an in-place
  alternative, define a queue/shovel with the same parameters, except the binding key which should be `regards.file.
  availability.status.*`. However, consider the recommendation below for improved security and efficiency.

### Recommended use of the exchange `regards.storage.file.notification`

If you had any queue or shovel bound to the exchange `regards.storage.file.notification`, it is now recommended to
define one queue or shovel **per project** bound the to the exchange, using the binding key
`regards.file.availability.status.<project>` where `<project>` is the project (or tenant) name.

## Frontend configuration

The default `staticConfiguration.js` has been removed from `regards-oss-frontend`: the frontend does not start without
it. The file must now be provided at deployment time and mounted in the frontend container at
`/var/www/conf-template/staticConfiguration.js`.

- **With the REGARDS Ansible roles**, the file is generated from the inventory (microservices and additional
  services) in the `config/regards/config/regards-oss-frontend/` folder of the stack, next to the
  `regards-oss-backend/` configuration folder, and mounted automatically.
- **Without them**, write your own file, store it with your other configuration files in the
  `config/regards/config/regards-oss-frontend/` folder of the stack and mount it at the path above.
  Start from the sample `webapp/webpack-config-front/src/conf/staticConfiguration.dev.js` in `regards-oss-frontend`,
  and adjust it to your needs.

:::note
The option `LEGACY_FRONTEND_CONFIGURATION: true` in the `front` microservice configuration is now required to deploy
versions prior to 2.5.0 with the Ansible roles.
:::
